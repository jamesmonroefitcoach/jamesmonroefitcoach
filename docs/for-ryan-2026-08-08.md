## 1. BLOCKER — monroefitcoach.com does not resolve

Everything below is pushed to `main` and Vercel will have built it, but **the
custom domain has no DNS records at all**, so none of it is reachable at the
usual address.

```
dig @8.8.8.8 monroefitcoach.com A      ->  status: NXDOMAIN, no answer
dig @8.8.8.8 www.monroefitcoach.com A  ->  status: NXDOMAIN, no answer
```

Checked against Google public DNS, not just a local resolver, so this is not a
caching artifact on one machine. NXDOMAIN means the name does not exist in DNS,
which is different from the site being down or the cert being broken.

Most likely causes, in order:

1. **Domain lapsed at the registrar.** Registrars pull the zone when a domain
   expires, and NXDOMAIN on both apex and `www` is the usual signature.
2. **Nameservers removed or repointed** at the registrar, so nothing delegates
   to Vercel any more.
3. The custom domain was never fully attached and the site only ever served from
   its `*.vercel.app` address.

Worth checking the registrar first, then Vercel → Project → Domains. The
`*.vercel.app` URL should still serve everything regardless, and is the fastest
way to confirm today's deploy is good.

Nothing in the repo needs changing for this. It is purely DNS/registrar.

## 4. The HEIC problem — fixed, and fixed for good

Three published photos were iPhone HEIC files. They uploaded and stored fine but
no browser can decode HEIC, so they rendered as empty frames on the live results
section. Katy Sheppard's card was two blank boxes.

**Existing three, repaired in storage.** Each object was overwritten in place
with JPEG bytes and an `image/jpeg` content type, keeping the exact same path.
Because the URL never changed, no `testimonials` row had to be edited, which
kept this out of §3. Untouched originals are backed up at
`testimonial-photos/_heic-originals/`, so it is reversible. Verified over the
wire: all three now return `200`, `content-type: image/jpeg`, and real JPEG
magic bytes (`ffd8ff`).

**Future uploads, handled automatically** (`197d920`). Conversion goes in at
`uploadFiles()` in `app/testimonials/actions.ts`, the single choke point both the
client submission form and the coach moderation upload share, so every path a
photo can enter by is covered. Two details worth knowing:

- Detection reads the ISO-BMFF `ftyp` brand from the file's first bytes rather
  than trusting the MIME type. One of the three broken uploads arrived with **no
  MIME type at all** and would have slipped past an extension or type check.
- If conversion throws, it stores the original rather than dropping the photo,
  and logs to `console.error`. Losing a client's photo is worse than storing one
  that needs a manual retry.

Uses `heic-convert` (pure JS, no native binaries, fine on Vercel). Lazily
imported so ordinary JPEG uploads do not pay for the WASM decoder.
